# Triage

Every issue carries one **category** (`bug` | `enhancement`) and one **state**:
`needs-triage` → `needs-info` | `ready-for-agent` | `ready-for-human` | `wontfix`; `needs-info` returns to
`needs-triage` when the reporter answers. The real label strings per repository are in `rules/triage-labels.yaml`.
An external pull request is an issue with code attached: same states, read against the diff.

Every comment you post starts with: `> *This was generated by AI during triage.*`

## Scan
Three buckets, oldest first, with counts and one line each: never triaged · `needs-triage` · `needs-info` where the
reporter has answered since the last notes.

## One issue
1. **Read it all** — body, comments, labels, dates, earlier triage notes (do not re-ask what was answered).
2. **Two checks against the code:** is it already implemented (search by concept, say where you looked)? was it
   rejected before (`docs/wow/_rejected/`)?
3. **Verify the claim** — reproduce the bug from the reporter's steps; for a pull request, check it out and run what it
   claims. Confirmed, failed, or not enough detail (a strong `needs-info` signal).
4. **Apply the outcome:**
   - `ready-for-agent` — post an agent brief ([references/agent-brief.md](references/agent-brief.md)).
   - `ready-for-human` — the same brief, plus why it cannot be delegated (a judgement call, an external access, a
     design decision).
   - `needs-info` — what is established so far, and the specific questions still open for the reporter.
   - `wontfix` — close with the reason: already implemented (point to where) · a rejected bug (a polite explanation) ·
     a rejected enhancement (record it in `_rejected/<concept>.md` and link it).

## Never
Edit code, plans or stage lists. Close anything except as `wontfix` with its reason. Turn a group of briefs into a
stage — that is the Planner's, through Bora.
